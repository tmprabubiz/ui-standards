# Coverage sheet — Field Recordings Library

Generated by the ui-standards skill. Keep this file in the app at
`docs/ui-standards/COVERAGE.md`. Agents resume from it in later sessions.

Catalogue version: 1.0.0 · Mode: ADVISE · Last updated: 2026-10-01

Nothing is built. Every Gate row is unchecked. The owner was not available, so every ADVISOR
question took its recommended option (or the owner's own brief) and is recorded below as an
assumption.

## Frame

```
App: A private web library where a documentary filmmaker uploads field-recording audio,
  previews it in a list, tags it, searches it, and shares chosen recordings (listen-only)
  with a sound editor.
People: One kind of user: a person with their own account. The filmmaker owns recordings.
  The sound editor is an ordinary second account that receives a view-only grant on
  individual recordings. No admin, no roles screen.
Screens: (1) Landing and sign in/up; (2) Library: recordings list with play, search,
  filters, upload; (3) Recording detail: player, details, tags, sharing, delete;
  (4) Recently deleted; (5) Shared with me; (6) Settings: profile, security, data;
  (7) First-run welcome; (8) Not-found, no-access, error, offline and maintenance pages.
Data: users, sessions, one-time tokens; recordings (original file, browser-playable preview,
  processing status, details); upload sessions; tags; grants and invitations; audit
  entries; background jobs; account export files.
Outside services: Email sending (provider undecided: Approval D5). Nothing else: no
  payments, maps, AI, analytics or webhooks out.
Platforms: Web, phone and computer.
Stack (recommended, none exists yet): React + TypeScript front end on an accessible
  headless base (Radix UI or React Aria); Node.js + TypeScript API; PostgreSQL for data,
  sessions, text search and the durable job queue; ffmpeg for audio processing; originals
  on a private storage volume behind a storage interface so the provider can change.
Assumptions (defaults taken):
  Q1  Accounts: email + password. No social sign-in.
  Q2  One kind of user. Sharing is a per-recording view-only grant to a named person; no
      members screen and no roles.
  Q3  Web on phone and computer.
  Q4  Things kept: recordings, tags, people with access.
  Q5  Audio uploads (answered by the brief). Allow-list: WAV/BWF, AIFF, FLAC, MP3, M4A/AAC,
      OGG/Opus. Nothing else.
  Q6  Recommended "Under 50" taken, but CORE D3 (a library can exceed 50) and the owner's
      request to search keep pagination and search in; cursor paging and server-side search.
  Q7  No bulk actions (one recording at a time).
  Q8  No notifications. Progress shows on screen; sharing is announced by email only if D5.
  Q9  Answered by the brief: share with the editor, read-only. Named-person grants only;
      no public links (D4).
  Q10 Deleted recordings go to a bin for 30 days (undo + Recently deleted). The automatic
      purge job is built but ships switched off until D13 is answered.
  Q11 No payments.
  Q12 Recommended "No" taken. Account emails are still personal data, so export and
      deletion (S12) are cast. Recordings are treated as private; place is a text label,
      never coordinates (D16).
  Q13 One language (English); all text kept in one strings place (CORE D4).
  Q14 Errors only: structured logs and health checks; no analytics.
  Q15 No integrations. No API keys, no webhooks out, no public API.
  Upload limit stays at the 25 MB default until D1 is answered (WAV files are often larger).
  Recording fields: title, recorded date, place (text), notes (plain text), tags.
  Shared view shows: title, recorded date, place, notes, tags, duration, and a playable
  preview with embedded location tags removed. No download for the editor (D3).
  Unverified accounts can sign in, browse and see a banner but cannot upload or share.
  Email is built behind a background job and a provider-neutral interface; in
  non-production it goes to a safe test inbox or the log. Production go-live waits on D5.
  Until D5/D7 the owner copies the one-time invitation link and sends it themselves; the
  link still requires signing in as the invited email.
  The owner gets no separate admin tools; no audit-log screen (S10 only records).
  Sessions are server-side cookies; no installed apps; single API version (own screens only).
Build order: S1, S13 (backups before any real recording is uploaded), S2, S3, S4, S6, S5,
  S7, S8, S9, S10, S11, S12.
```

## Slice contracts

```
Slice S1 · App frame, navigation and error pages
Goal: Anyone opening the app lands in a consistent, responsive frame, can move around by
  keyboard or touch, and gets a clear page when something is missing, forbidden or broken.
Screen: Public landing; signed-in shell (navigation, account menu, skip link); not-found,
  no-access, unexpected-error, offline and maintenance pages (FE-SHELL-01, -02, -03, -04,
  -06). Toasts (FE-FEED-01) and dialogs (FE-FEED-03) are shared by every later slice.
API: Owns no data endpoints. Platform rules apply to all: resource contract (BE-API-01),
  problem+json errors with request_id (BE-API-02), server validation (BE-API-03), security
  headers/CORS/CSRF (BE-OPS-05), config and secrets (BE-OPS-01), structured logs
  (BE-OPS-02). The host serves the app shell for every client route; unknown /api paths
  return a 404 problem body. Called by: every screen.
Data: Schema conventions and numbered migrations (BE-DATA-01, BE-DATA-02): random ids,
  created_at/updated_at, non-null owner_id on user data, indexes on foreign keys and filter
  columns. No user data yet.
Permissions: Public pages need no sign-in. Every later endpoint names its own rule (F11).
States: loading (shell skeleton), error (page with Retry and request id), no-permission
  (same wording as not-found when existence is sensitive), partial (a failed region keeps
  the rest of the page usable), empty n/a.
Checks: FE-SHELL-01/02/03/04/06 acceptance 1–4; FE-FEED-01/03 acceptance 1–4; BE-API-01/02/03
  acceptance 1–4; BE-DATA-01/02 acceptance 1–4; BE-OPS-01/02/05 acceptance 1–4
```

Slice S2 · Accounts: sign up, verify, sign in/out, reset password
Goal: A person creates an account, proves their email, signs in and out safely, and
  recovers a forgotten password.
Screen: Sign up, Check your inbox, Verify result, Sign in, Forgot password, Reset password,
  Signed out confirmation, unverified-account banner (FE-ACCT-01, -02, -03; forms per
  FE-FORM-01, -02)
API: POST /accounts {email, password} → 201 (called by Sign up; rate limited, key per BE-OPS-04)
  POST /accounts/verify-email {token} (Verify result)
  POST /accounts/verify-email/resend (Check your inbox, banner)
  POST /sessions {email, password} → sets cookie (Sign in)
  DELETE /sessions/current → 204 (account menu: Sign out)
  GET /me → {id, email, verified, …} (shell account menu, banner)
  POST /password-resets {email} → always 202 (Forgot password)
  POST /password-resets/confirm {token, new_password} (Reset password)
  POST /webhooks/email-events (called by the email provider only; signature verified,
  BE-JOB-06; inert until D5)
  Jobs: send-verification, send-reset, send-password-changed (BE-JOB-03 via BE-JOB-01)
Data: users(id, email unique lower-case, password_hash, email_verified_at, …);
  sessions(id hash, user_id, created_at, last_seen_at, idle_expires_at, absolute_expires_at,

  email_log, suppressed_addresses, webhook_events(event_id unique); rate-limit counters
Permissions: sign-up, sign-in, reset and the webhook are the only unauthenticated routes,
  each rate limited. GET /me and DELETE /sessions/current act only on the caller's own
  session (F11). Verification and reset tokens are single-use and hashed at rest.
States: loading (busy submit), error (generic sign-in failure, field errors, summary),
  disabled (throttled: "try again in N seconds"; unverified: upload/share explain why),
  empty n/a, partial n/a
Checks: FE-ACCT-01/02/03 acceptance 1–4; FE-FORM-01/02 acceptance 1–4; BE-AUTH-01/02/04

Slice S3 · Upload recordings
Goal: The owner uploads one or many audio files, even large ones over a weak connection,
  sees progress per file, and sees each recording become ready to play.
Screen: Upload panel on the Library (FE-FORM-04) with per-file progress and processing status
  (FE-FEED-04); title and recorded date prefilled and editable (FE-FORM-01/02 rules)
API: POST /uploads {filename, size, content_type, Idempotency-Key} → 201 upload session
    (Upload panel; BE-FILE-04, BE-API-06)
  PUT /uploads/{id}/parts/{n} + checksum header (Upload panel)
  GET /uploads/{id} → received offset, state, recording status (Upload panel; resume/refresh)
  POST /uploads/{id}/complete → 202 {recording id, status processing} (Upload panel)
  DELETE /uploads/{id} → 204 (Cancel)
  POST /recordings/{id}/retry-processing → 202 (Retry on a failed file)
  Jobs: process-recording (sniff and validate, read duration, make browser-playable
  preview with location tags removed; BE-FILE-03 via BE-JOB-01); expire-upload-sessions
  (BE-JOB-02, scheduled in S9)
Data: upload_sessions(id, owner_id, size, received, expires_at, state); recordings(id, owner_id,
  original_key, preview_key, size_bytes, format, duration_ms, status pending|processing|ready|
  failed, failure_code, …; full fields in S6); jobs; per-user storage quota
Permissions: signed-in, email-verified user; an upload session is usable only by its creator
  (F11); quota and rate limits per user; type allow-list by content sniffing; 25 MB limit
  until D1
States: loading (busy, progress), empty n/a, error (per-file with reason code and Retry),
  partial (4 of 5 done, 1 failed), disabled (unverified, over quota, explained)
Checks: FE-FORM-04 acceptance 1–4; FE-FEED-04 acceptance 1–4; BE-FILE-01/02/03/04 acceptance 1–4;
  BE-JOB-01 acceptance 1–4; BE-API-06 acceptance 1–4
