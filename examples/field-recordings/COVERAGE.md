# Coverage sheet — Field Recordings Organiser

Generated by the ui-standards skill. In a real app this file lives at
`docs/ui-standards/COVERAGE.md`; this copy is the worked example. Agents resume from it in later sessions.

Catalogue version: 1.0.0 · Mode: ADVISE · Last updated: 2026-10-01

## Frame

```
App: A web app where a documentary filmmaker uploads field audio recordings, previews them
     in a list, tags and searches them, and shares chosen ones with a sound editor.
People: One account holder (the filmmaker, "owner"). The sound editor is a read-only guest
        of the specific recordings the owner shares. No other kinds of user.
Screens: Landing / sign in · Sign up · Reset password · Library (list, search, filters,
         bulk actions) · Upload · Recording detail (player, name, tags, sharing) ·
         Shared with me · Recently deleted · Settings (profile, security, data) ·
         Not-found and error pages
Data: Accounts and sessions · recordings (audio file, browser preview, duration, status) ·
      tags · recording-tag links · shares and invitations · background jobs · audit log ·
      one-time tokens · export and deletion requests
Outside services: Email provider (not chosen yet; stubbed behind a setting) · file storage
                  and hosting (choice pending). No payments, maps, AI or analytics.
Platforms: Web, working on phone and computer.
Stack (recommended, owner to confirm): TypeScript throughout. React with React Aria
       Components (accessible base) built with Vite. Node.js REST API (Fastify) with an
       OpenAPI description. PostgreSQL (migrations, full-text search, Postgres-backed job
       queue). Private S3-compatible object storage; resumable uploads through the server;
       ffmpeg for previews. Argon2id password hashing. Hosting is an Approval item.
Assumptions (defaults taken, owner not available this session):
  Q1  Accounts with email + password (no social sign-in).
  Q2  One kind of user. The editor is a guest with a view-only share, not a role.
  Q3  Web on phone and computer.
  Q4  The app keeps recordings, tags and shares.
  Q5  Audio files only, up to 2 GB each, resumable upload (the brief says field recordings).
  Q6  Hundreds of recordings per person (the brief says "library"); search still built.
  Q7  Yes, act on many at once (tag, untag, delete, share). Inferred from "organise".
  Q8  No notification centre; only account, security and invitation emails.
  Q9  Share read-only. The editor must have an account and sign in; links that open without
      sign-in are an Approval item. The editor hears and previews the recording but cannot
      download the original until the owner approves it.
  Q10 Recoverable: a bin for 30 days. The automatic purge ships switched off until approved.
  Q11 No payments.
  Q12 Some personal data (accounts, and voices in recordings). The owner is responsible for
      consent from people recorded; the app stores no sensitive categories.
  Q13 One language (English). Text is kept in one strings place per screen (CORE D4).
  Q14 Errors only (logs and health checks); no usage analytics.
  Q15 No outside systems connect to it.
  Extra: unverified email may still use the app but cannot share; the header is not sticky;
         the email provider is a stub until approved; account erasure ships switched off
         until approved; time zone is detected from the browser.
```

## Slice contracts

```
Slice S1 · Open the app on any device and never get lost
Goal: A visitor or the owner opens the app on phone or computer, sees the same frame
      everywhere, reaches any screen by address, and always lands somewhere helpful when a
      page is missing or something fails. This slice also lays the conventions every later
      slice builds on.
Screen: Public landing, app shell (nav, account menu, skip link), not-found / no-access /
        error pages, status message area (FE-SHELL-01, -02, -03, -04, -06, FE-FEED-01)
API: GET /healthz, GET /readyz (BE-OPS-03). Every API path answers errors as problem details
     with a stable code and request id (BE-API-02); unknown /api paths return 404 in that
     format. Resource, validation and header conventions for all later endpoints
     (BE-API-01, BE-API-03, BE-OPS-05). Client-routed addresses are served for refresh.
Data: Migration runner and applied-migrations table (BE-DATA-02); schema conventions
      (ids, timestamps, owner column, constraints, BE-DATA-01); dev/test demo seed with fake
      accounts and recordings (BE-DATA-06); example configuration file, startup config
      check, structured request logs (BE-OPS-01, BE-OPS-02).
Permissions: Landing and error pages are public; health responses expose no internals;
             a protected address opened signed-out goes to sign-in and back (F11).
States: loading, error (page and region), disabled / no permission (not found, no access),
        offline. Empty and partial belong to later screens.
Checks: FE-SHELL-01/02/03/04/06 acceptance 1–4; FE-FEED-01 1–4; BE-API-01/02/03 1–4;
        BE-DATA-01/02/06 1–4; BE-OPS-01/02/03/05 1–4

Slice S2 · Create an account, sign in and out, recover access
Goal: A new person creates an account, confirms their email, signs in, signs out, and can
      reset a forgotten password without revealing which emails are registered. A new
      account lands on a first-run Library that explains what to do.
Screen: Sign up, Check your inbox, Sign in, Forgot password, Reset password, first-run empty
        Library (FE-ACCT-01, -02, -03, -05; FE-FORM-01, -02)
API: POST /api/auth/signup · POST /api/auth/verify-email · POST /api/auth/resend-verification ·
     POST /api/auth/signin · POST /api/auth/signout · POST /api/auth/password-reset/request ·
     POST /api/auth/password-reset/confirm · GET /api/me (BE-AUTH-01, -02, -04)
Data: users (id, email, email_verified_at, password_hash, display_name, time_zone,
      onboarding_done_at, timestamps) · sessions (hashed id, user_id, idle and absolute
      expiry, last_used) · one_time_tokens (hash, user_id, purpose, expires_at, used_at) ·
      email_outbox (every send recorded; stub provider logs instead of sending) ·
      jobs (BE-JOB-01) · audit_log (BE-DATA-04) · rate-limit counters (BE-OPS-04)
Permissions: Sign-up, sign-in and reset endpoints are public and rate limited. /api/me and
             sign-out need a session. Every later endpoint is deny-by-default with an
             object-level check (BE-AUTH-05, F11).
States: loading, error (field and whole form), disabled (busy, throttled with wait time),
        no permission (expired or used link)
Checks: FE-ACCT-01/02/03/05 1–4; FE-FORM-01/02 1–4; BE-AUTH-01/02/04/05 1–4; BE-OPS-04 1–4;
        BE-JOB-01/03 1–4; BE-DATA-04 1–4

Slice S3 · Upload field recordings
Goal: The owner chooses one or many audio files (some over 1 GB), watches each upload, and
      ends up with recordings that are processed into a browser-playable preview.
Screen: Upload panel in the Library with per-file list, progress, cancel, retry, and
        "Processing" status (FE-FORM-04, FE-FEED-04)
API: POST /api/uploads {filename, size, type} with Idempotency-Key → upload session ·
     HEAD and PATCH /api/uploads/{id} (resumable parts, offset acknowledged) ·
     POST /api/uploads/{id}/complete · DELETE /api/uploads/{id} (cancel) ·
     GET /api/recordings/{id} (status) · job: process recording into preview and duration
     (BE-FILE-01, -02, -03, -04, BE-API-06)
Data: upload_sessions (owner, declared size, received offset, expires_at) ·
      recordings (id, owner_id, title [defaults to file name], display_filename, storage_key,
      preview_key, mime_type, size_bytes, duration_ms, status pending/processing/ready/failed,
      failure_code, deleted_at, version, timestamps) · per-user storage total (quota)
Permissions: Signed-in owner uploads for themselves only; an upload session is usable only
             by its creator; files are private (F11).
States: loading, error, partial (some files failed, others fine), disabled (busy, limit
        reached), processing (pending / processing / failed with Retry)
Checks: FE-FORM-04 1–4; FE-FEED-04 1–4; BE-FILE-01/02/03/04 1–4; BE-API-06 1–4

Slice S4 · Browse the library, filter it, preview recordings
Goal: The owner scrolls a list of recordings, plays any one to preview it (one at a time),
      narrows the list by tag, status and date, and opens a recording for the full player.
Screen: Library list with play buttons (FE-COLL-02, FE-MEDIA-01, FE-COLL-04, FE-COLL-05) ·
        Recording detail with player (FE-COLL-06, FE-MEDIA-02)
API: GET /api/recordings?cursor&page_size&sort&status&tag&date_from&date_to ·
     GET /api/recordings/{id} · GET /api/recordings/{id}/media → short-lived signed preview
     address with range support (BE-API-04, BE-FILE-02)
Data: Shown fields all exist: title, duration, status, tags (S5), created_at. Indexes on
      owner_id + created_at, status, and tag links (BE-DATA-01).
Permissions: Owner only; a recording owned by anyone else returns 404 (F11).
States: loading (skeleton rows), empty (nothing yet) vs no results (filters active),
        error with Retry, partial (a preview fails on one row only), disabled (still processing)
Checks: FE-COLL-02/04/05/06 1–4; FE-MEDIA-01/02 1–4; BE-API-04 1–4

Slice S5 · Name and tag a recording
Goal: The owner renames a recording and attaches tags by typing, creating new tags on the fly.
Screen: Details form on Recording detail with tag input (FE-FORM-05, FE-SEL-03)
API: PUT /api/recordings/{id} {title, tag_ids[], version} with If-Match ·
     GET /api/tags?q=&limit= · POST /api/tags {name} (BE-API-07)
Data: tags (id, owner_id, name, name_key unique per owner, timestamps) ·
      recording_tags (recording_id, tag_id, owner_id, created_at; unique pair) ·
      recordings.version (changes on every write)
Permissions: Owner only. Tag ids in a request must belong to the same owner (F11, no mass
             assignment).
States: loading tag options, empty ("No matches", offer Create), error, conflict (edit made
        in another tab)
Checks: FE-FORM-05 1–4; FE-SEL-03 1–4; BE-API-07 1–4

Slice S6 · Search recordings
Goal: The owner types words and finds recordings by title, tag or file name, and can share
      or refresh the result.
Screen: Search box in the Library (FE-COLL-03)
API: GET /api/recordings?q= — the same list endpoint, rate limited, paged, accent- and
     case-insensitive (BE-DATA-07, BE-API-04)
Data: search index column over title, tag names and display_filename, rebuilt when title or
      tags change; deleted recordings excluded
Permissions: Owner only, applied inside the query itself (F11).
States: loading, empty vs no results, error, disabled (query too short)
Checks: FE-COLL-03 1–4; BE-DATA-07 1–4

Slice S7 · Delete a recording and get it back
Goal: The owner deletes a recording, can undo straight away, finds it in Recently deleted for
      30 days and restores it; "Delete forever" is a separate deliberate action.
Screen: Delete on list and detail, confirm dialog, undo message, Recently deleted view
        (FE-FEED-02, FE-FEED-03)
API: DELETE /api/recordings/{id} (soft delete) · POST /api/recordings/{id}/restore ·
     GET /api/recordings?deleted=true · DELETE /api/recordings/{id}/permanent (audited) ·
     scheduled job: purge after 30 days, switched off until approved (BE-DATA-03, BE-JOB-02)
Data: recordings.deleted_at and deleted_by; unique rules ignore deleted rows; the purge job
      also removes stored files and stops any shares of that recording
Permissions: Owner only; permanent delete is an explicit separate action and is audited.
States: loading, error (not deleted — item stays), disabled (busy), empty bin
Checks: FE-FEED-02 1–4; FE-FEED-03 1–4; BE-DATA-03 1–4; BE-JOB-02 1–4

Slice S8 · Tag, untag or delete many recordings at once
Goal: The owner selects several recordings and applies one action to all, seeing exactly which
      ones failed.
Screen: Library selection mode and action bar (FE-SEL-01)
API: POST /api/recordings/bulk/tags-add · /bulk/tags-remove · /bulk/delete · /bulk/restore
     {ids[≤100], tag_id?} → {results[{id, ok, error?}]} (BE-API-05)
Data: Uses recording_tags and recordings.deleted_at; no new fields
Permissions: Owner of each recording only; checked per item (F11).
States: loading, error, partial (some failed, stay selected), disabled (nothing selected)
Checks: FE-SEL-01 1–5; BE-API-05 1–4

Slice S9 · Share recordings with my sound editor
Goal: The owner invites the editor to specific recordings, sees who has access, and can revoke
      it at any time. The editor accepts, signs in, sees "Shared with me", and plays previews.
Screen: Share dialog (single and bulk), "Shared with" section on detail, Accept invitation,
        Shared with me list, shared recording detail (play only) (BE-AUTH-06; reuses
        FE-FEED-03, FE-COLL-02, FE-MEDIA-01, FE-MEDIA-02)
API: POST /api/shares {recording_ids[], email, message?} with Idempotency-Key → per-recording
     results · GET /api/recordings/{id}/shares · DELETE /api/shares/{id} (revoke) ·
     POST /api/shares/{id}/resend · POST /api/invitations/accept {token} ·
     GET /api/shared-with-me · GET /api/shared-with-me/{recording_id} ·
     GET /api/shared-with-me/{recording_id}/media → preview address only
Data: shares (id, recording_id, owner_id, invited_email, grantee_user_id, level = view,
      status pending/active/revoked/expired, token_hash, expires_at default 7 days,
      accepted_at, timestamps); every invite, accept, resend and revoke is audited
Permissions: Only the recording owner creates, resends or revokes. The guest can read a
             shared recording and its preview, nothing else. Revoked, expired or foreign
             links return 404. Invitation email goes through the stub until the provider is
             approved; until then the owner sees a copyable invitation link to pass on.
States: loading, empty (nothing shared yet), error, partial (some recordings not shareable),
        disabled (recording still processing, in the bin, or email not yet verified),
        no permission (revoked or expired)
Checks: BE-AUTH-06 1–4; reused entries re-checked on the shared screens

Slice S10 · Manage my profile, password and sign-ins
Goal: The owner updates their name and time zone, changes email or password, and signs out
      other devices.
Screen: Settings: Profile, Security (password, active sessions) (FE-ACCT-04)
API: GET and PUT /api/me/profile {display_name, time_zone, version} · POST /api/me/email-change ·
     POST /api/me/password {current, new} · GET /api/me/sessions ·
     DELETE /api/me/sessions/{id} · POST /api/me/sessions/revoke-others ·
     POST /api/auth/reauthenticate
Data: users, sessions, one_time_tokens (email change); audit entries for each sensitive change
Permissions: Own record only; email, password and data actions need recent sign-in (F11).
States: loading, error (setting reverts to saved value), disabled (busy)
Checks: FE-ACCT-04 1–4

Slice S11 · Download my data and delete my account
Goal: The owner downloads everything held about them, or deletes their account after a
      14-day grace period with a clear list of what goes and what stays.
Screen: Settings › Data: Download my data, Delete my account (FE-ACCT-06)
API: POST /api/me/exports (202) · GET /api/me/exports/{id} · expiring download link ·
     POST /api/me/deletion {password, confirmation} · DELETE /api/me/deletion (cancel) ·
     jobs: build export, erase account after grace period, switched off until approved
     (BE-OPS-06)
Data: exports (user_id, status, file key, expires_at) · deletion_requests (user_id,
      scheduled_for, cancelled_at) · a minimal audit marker kept after erasure
Permissions: Own data only; recent sign-in required; export link is single-use, expiring and
             checked against the owner (F11).
States: loading, empty, error, partial (export includes some but not all files), disabled
        (grace period running, shows date and Cancel)
Checks: FE-ACCT-06 1–4; BE-OPS-06 1–4

Slice S12 · Launch safely: deploy, back up, restore
Goal: The app can be released and rolled back repeatably, and the owner's recordings and
      database can be restored after a failure.
Screen: None (operations). Non-production builds show an environment label; planned
        maintenance shows the 503 page from S1.
API: Deploy pipeline from the repository · backup and backup-failure jobs · restore runbook
Data: Backup run records (time, outcome, size) · separate secrets, database and storage per
      environment
Permissions: Named people only for backups, restore and production access (F12).
States: not applicable to screens; failed backups and failed health checks alert the owner
Checks: BE-OPS-07 1–4; BE-DATA-05 1–4
```
